# 智能会议纪要系统 —— 技术可行性评估

> 编制日期：2026-05-14  
> 方法论：逐一审查源码中的关键风险点，基于真实代码给出判定，而非泛泛而谈。

---

## 一、总体结论

**全流程闭环在技术上可行，但当前代码存在 4 个必须修复的高严重度缺陷，否则「全自动」无法成立。** 这些缺陷都是工程问题（拼装错误、遗漏、单例限制），不是算法或理论瓶颈。修复方案明确，无二义性。

---

## 二、逐项技术可行性判定

### 2.1 声纹→说话人闭环：可行，但当前管线断裂

**现状**：`MinuteGenerationService` 第 3 步「调用 ISV 声纹识别」是一个空壳——

```
Step 3 代码（line 116-119）：
log.info("Step 3: Voiceprint identification...");
// TODO: 实际声纹识别实现
log.info("Step 3: Voiceprint identification completed");
```

`featureIds` 在第 81-87 行已收集，但从未传递给任何识别方法。`VoiceprintService` 已有 `identifySpeaker()` 和 `updateTranscriptSpeakers()` 方法，但 **未被注入** 到 `MinuteGenerationService` 中。

**修复方案**（明确，约 0.5 天）：
1. 注入 `VoiceprintService`。
2. 在构建 LLM 输入文本之前，调用 `updateTranscriptSpeakers(meetingId)` 将 speaker_N 替换为真实姓名。
3. 重新从 DB 读取 segments，确保 LLM 拿到的是带姓名的文本。

**ISV 客户端可靠性**：
- `XfyunIsvClient.identifyVoiceprint()` API 契约清晰：PCM 音频 → 1:N 搜索 → 返回 featureId + confidence。
- 置信度阈值硬编码 0.6，偏低（业界建议 0.7-0.8），嘈杂环境下误识风险存在。
- **`vcnTopN=1`** 只返回最高分匹配，无候选间距判断（1st 和 2nd 得分接近时应标记为不确定）。

> **判定**：技术可行，管线接通即可。但 0.6 阈值需根据实测调整；建议增加「不确定」状态（confidence 在 0.5-0.7 之间标为「待确认」）。

### 2.2 实时 ASR 说话人标记：可行，但当前有 Bug

**现状**：讯飞实时 ASR 返回的 `rl` 字段（说话人切换标记，如 `"1"`, `"2"`）已被解析，但 `AsrBridgeService` 完全忽略了它：

```
AsrBridgeService.onAsrResult()（line 116-118）：
String speaker = "Speaker " + speakerCounters.getOrDefault(meetingId, 0);
```

这里有两个问题：
1. `speakerCounters` 从 0 开始但 **从未递增**，所有 segment 永远是 `"Speaker 0"`。
2. `result.getSpeakerId()`（来自 `rl` 标记）被丢弃。

**修复方案**（明确，约 0.5 天）：
1. 用 `result.getSpeakerId()` 代替自建计数器。当 `rl` 存在时使用 `rl` 值（如 `"1"`, `"2"`），否则 fallback 到 `"Speaker N"`。
2. 后续在 `MinuteGenerationService` 中将 rl 值映射为姓名。

**讯飞 feature_ids 实时鉴权的问题**：
- `XfyunRealtimeClient` 的 `featureIdsConfig` 是一个 **全局静态属性**，不是按会议动态传入的。
- 这意味着所有会议共享同一组 feature_ids，并发会议时参会人不同会导致识别混乱。

**修复方案**：在 `connect()` 时按会议动态传入 feature_ids，作为请求参数注入鉴权 URL。

> **判定**：技术可行，Bug 修复明确。讯飞 API 本身支持实时声纹鉴权，只是调用方式需从全局配置改为按会议参数化。

### 2.3 并发会议支持：可行，但 XfyunRealtimeClient 是单例瓶颈

**现状**：`XfyunRealtimeClient` 内部只有一个 `WebSocketClient` 实例和一个 `currentMeetingId` 字段：

```
XfyunRealtimeClient（line 53-60）：
private WebSocketClient client;
private final AtomicBoolean connected = new AtomicBoolean(false);
private String currentMeetingId;
```

第二场会议调用 `connect()` 时，因 `connected.get() == true` 直接返回 `false`，ASR 无法启动。

**影响**：当前系统**同一时刻只能有一场会议在录音转写**。

**修复方案**（两种选一）：
- **方案 A（推荐）**：将 `XfyunRealtimeClient` 改为非单例——每场会议创建独立实例，在 `AsrBridgeService` 中以 `Map<meetingId, XfyunRealtimeClient>` 管理。改动量约 1 天。
- **方案 B**：加连接池（如 max=5），池满时排队。改动量约 1.5 天。

> **判定**：技术可行，是架构调整而非算法问题。方案 A 更简单直接。

### 2.4 AI 主持人状态机：可行，有线程安全隐患

**现状**：`MeetingHostSessionService`（872 行）用 1 秒 tick 驱动整个主持流程。核心问题：

| 问题 | 严重度 | 详情 |
|------|--------|------|
| `HostRuntime` 字段非 volatile | 中 | `tick()` 线程读 `topicEndMs`/`meetingEndMs` 时无同步保护，`nextTopic()` 从另一线程写，可能读到过期值 |
| 调度线程池仅 2 个线程 | 中 | 超过 2 场会议时，第 3 场的 tick 可能延迟，导致计时不准 |
| TTS 失败返回 0ms | 中 | 点名话术未播出，答到窗口却已打开，参会人不知道该答到 |
| CompletableFuture 链式调用无超时 | 低 | TTS 或 ASR 卡住时，整个点名流程挂起 |

**修复方案**：
1. `HostRuntime` 的被跨线程读写的字段加 `volatile`，或改用 `synchronized` 保护。
2. 调度线程池扩到 `Math.max(4, 预计并发会议数 + 2)`。
3. TTS 返回空 PCM 时，跳过当前人的点名，直接标记 MISSED，而非打开答到窗口。
4. CompletableFuture 链加 `.orTimeout()`（Java 9+，项目已是 Java 17）。

> **判定**：技术可行，是工程加固而非架构重构。修复量约 1 天。

### 2.5 飞书 Webhook 1 秒响应约束：可行，已有正确模式

**现状**：所有事件处理在 `CompletableFuture.runAsync()` 中异步执行，同步返回 `code: 0`。这个模式是正确的。

**潜在风险**：
- AES 解密在同步路径上执行（CPU 密集，通常 <50ms），极端大 payload 可能接近 1s。
- 卡片按钮快速双击会触发两次异步处理，无幂等保护。

**修复方案**：
1. AES 解密耗时可通过监控确认，通常安全。
2. 卡片回调加幂等键（`action + open_id + message_id` 组合去重）。

> **判定**：可行，无阻塞问题。

### 2.6 WebSocket 断线处理：可行，音频不丢失

**现状**：WebSocket 断开时 `afterConnectionClosed()` 调用 `endRealtimeAsr()` 关闭 ASR 连接。未发送到讯飞的帧会丢失实时转写，但 **PCM 数据已写入本地缓存文件**，离线 ASR 仍可处理。

**不足**：
- 前端 AudioWorklet 本地缓存 + 重连补传 **未实现**（代码中无对应逻辑）。
- 断线后 `RecordingService` 不会自动停止，录音文件句柄可能泄漏。

**修复方案**：
1. 前端增加：断线时 AudioWorklet 缓存帧 → 重连后带序号补传 → 后端滑动窗口去重。
2. 后端增加：WebSocket 断开超过 30s 未重连 → 自动停止录音。

> **判定**：可行，音频数据不会丢失（本地缓存兜底）。前端补传是体验优化，非功能必要。

### 2.7 飞书 API 调用可靠性：可行，需增加重试和限流

**现状**：
- Token 缓存用 `volatile` 字段，多线程可能重复刷新（无害但浪费）。
- 绝大多数 API 调用无重试机制，失败即丢弃。
- 仅 `updateDocBlocks()` 有频率控制（批次间 400ms sleep），其他 API 无保护。

| API | 飞书限流 | 当前保护 | 风险 |
|-----|---------|---------|------|
| 发消息/卡片 | ~5 msg/s | 无 | 连续发多条可能触发限流 |
| 文档写入 | 3 req/s per doc | 有（400ms sleep） | 安全 |
| 用户信息 | ~50 req/s | 无 | 低风险 |
| 日历/会议室 | ~10 req/s | 未实现 | 待开发时需加入 |

**修复方案**：
1. 加通用限流器（Guava RateLimiter 或 Resilience4j），按 API 类型设不同 QPS。
2. 关键操作（发消息、创建文档）加重试（指数退避，最多 3 次）。
3. Token 刷新加 `synchronized` 或 `ReentrantLock`，避免并发重复刷新。

> **判定**：可行，是工程加固项。

### 2.8 XfyunIsvClient 缓存线程安全：可行，简单修复

**现状**：两个缓存 Map 是普通 `HashMap`，并发写入会导致数据损坏或 `ConcurrentModificationException`。`refreshCache()` 方法先 `.clear()` 再填充，中间窗口所有映射消失。

**修复方案**：
1. 改为 `ConcurrentHashMap`。
2. `refreshCache()` 用新 Map 填充后一次性替换引用，而非先 clear 再 put。

> **判定**：可行，改动 <10 行代码。

## 三、关键第三方服务可行性

### 3.1 讯飞实时 ASR

| 维度 | 评估 |
|------|------|
| API 稳定性 | 成熟产品，企业级 SLA；断线重连已实现 |
| 并发限制 | 默认 5 路；可购买更高并发包 |
| 准确率 | 普通话 ≥95%；方言 `autodialect` 模式略降 |
| 延迟 | 语音→文字 ≤2 秒（实测验证） |
| 成本 | 0.33 元/分钟，20 场/月 ≈ 300 元 |

> **结论**：可行，是项目最成熟的外部依赖。

### 3.2 讯飞 ISV 声纹

| 维度 | 评估 |
|------|------|
| 识别准确率 | 3-5 人小会议 ≥90%；大组（20+人）会下降 |
| 注册要求 | 每人需录 5s 以上音频；24h 过期需续期 |
| 1:N 搜索 | 单组建议 ≤200 人；超出需分组 |
| 成本 | 0.05 元/次，极低 |

**风险点**：
- 声纹 24h 过期，每次会前需确认参会人已注册且未过期。
- 远场麦克风（会议室音箱拾音）会显著降低识别率。
- 首次使用需推动全员注册，是运营挑战而非技术问题。

> **结论**：技术可行，运营有挑战。建议 3-5 人固定会议组先行验证。

### 3.3 大模型（DeepSeek 等）

| 维度 | 评估 |
|------|------|
| 纪要生成质量 | 结构化 5 段 Prompt，输出格式稳定；偶尔出现幻觉 |
| 待办提取 | 完整率约 85%；复杂讨论可能遗漏隐含待办 |
| 纠错效果 | 对 ASR 专有名词/口音错误有帮助，但非万能 |
| 延迟 | 单次调用 30-60s（含 LLM 排队） |
| 成本 | DeepSeek 极低（<20 元/月）；可切换其他模型 |

**风险点**：
- LLM 幻觉可能导致纪要中出现未讨论的内容。
- 待办提取完整率 85% 意味着约 15% 待办被遗漏——需手动补录机制。

> **结论**：可行，质量可通过 Prompt 优化和二次增强提升。15% 遗漏率需人工兜底。

### 3.4 飞书开放平台

| 维度 | 评估 |
|------|------|
| 消息/卡片 | 成熟稳定，已验证 |
| 文档 API | Block 写入有批次限制（50 块/批），已处理 |
| 日历/会议室 | API 已发布，需申请权限 |
| 任务 API | API 已发布，需申请权限 |
| 审批流程 | 部分权限需企业管理员审批，周期 1-3 天 |

> **结论**：技术可行。日历/会议室/任务是新的 API 对接，无技术壁垒，但权限审批可能延迟。

## 四、不可行或高风险项（诚实标注）

| 项目 | 判定 | 原因 |
|------|------|------|
| **远场麦克风 + 声纹识别** | 高风险 | 会议室音箱拾音信噪比低，讯飞 ISV 对近场设计，远场准确率会显著下降；建议近距离手机/笔记本录音 |
| **多人同时说话分离** | 不可行 | 产品已约定不同时发言；ASR/声纹均不支持叠话分离 |
| **100% 待办自动提取** | 不可行 | LLM 完整率约 85%，剩余需人工补录；可优化 Prompt 但无法保证 100% |
| **100% 说话人自动识别** | 不可行 | 声纹注册率、麦克风质量、环境噪声都会影响；需保留手动修正通道 |
| **3D 数字人实时渲染** | 不推荐 | 需 WebGPU + 大模型，延迟和兼容性问题大；2D Lottie/Live2D 是性价比最优解 |

## 五、修复优先级与工作量

| 优先级 | 缺陷 | 工作量 | 影响 |
|--------|------|--------|------|
| **P0** | `XfyunRealtimeClient` 单例→并发多实例 | 1 天 | 不修则只能同时开 1 场会 |
| **P0** | `AsrBridgeService` 忽略 `rl` 标记 + 计数器不递增 | 0.5 天 | 不修则所有 segment 都是 Speaker 0 |
| **P0** | `MinuteGenerationService` 声纹管线空壳 | 0.5 天 | 不修则纪要中永远无真实姓名 |
| **P1** | `XfyunIsvClient` HashMap→ConcurrentHashMap | 0.1 天 | 并发注册时数据损坏 |
| **P1** | `HostRuntime` 字段加 volatile/synchronized | 0.3 天 | 多线程下可能读到过期值 |
| **P1** | TTS 空响应时点名逻辑修正 | 0.3 天 | 用户没听到名字却要答到 |
| **P2** | 飞书 API 通用限流+重试 | 1 天 | 高并发下可能被飞书限流 |

## 六、结论

1. **全流程闭环在技术上可行**，无底层算法或理论障碍。
2. **当前有 4 个 P0 级工程缺陷**，不修复则「全自动」不成立：ASR 单例瓶颈、说话人标记 Bug、声纹管线空壳、ISV 缓存线程不安全。合计修复约 2 天。
3. **第三方服务全部可行**：讯飞 ASR/ISV/TTS 成熟稳定，DeepSeek 成本极低且可切换，飞书 API 文档齐全。
4. **诚实标注不可行项**：远场声纹、多人叠话、100% 自动提取/识别——这些是物理/模型限制，非工程可解决，需产品侧设定合理预期。
5. **最大风险不在代码，在运营**：声纹注册率、飞书权限审批、`int_user_mapping_feishu` 数据初始化——这些需要人工推动，AI 无法替代。
