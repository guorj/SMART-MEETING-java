## 一、整体评估结论

| 方案 | 时间 | 说明 |

| 当前图表 | 12周 | Phase 3 每周工作量偏重，飞书审批可能阻塞 |
| 建议调整 | 14周 | Phase 3 扩为 4 周（W5-W9), Phase 4 推后到 W10-W14; Phase 3 预留飞书审批风险缓冲 |

## 二、逐 Phase 详细审核

### Phase 1（W1-W2）会中闭环 —— 合理，但有 4 个遗漏
图表内容：声纹管线打通、安全加固  
评估报告对照： W1 壚纹管线 + 离线校正， W2 做安全加固 + 断线补传 + 手动修正

**合理性判定**:
- ✅ 声纹管线打通（0.5天） -> 合理。 `MinuteGenerationService` 的 TODO 补全，工作量确实约 0.5 天
- ⚠️ 离线校正修复遗漏 | 评估报告 W1 包含离线校正写回（2天工作量)，这是声纹闭环的前置依赖。图表标注为「声纹管线打通', 但离线校正作为隐含部分
- ✅ 安全加固（密钥环境变量化） -> 合理。 3天工作量,放 W2 合适
- ⚠️ 断线补传未标注 | 评估报告 W2 包含前端 AudioWorklet 缓存帧 + 补传逻辑（生产可用的必要条件), 图表未标注
- ⚠️ 手动修正指令未标注 | 评估报告 W2 包含 rename_speaker / regenerate_minutes（2天工作量,声纹识别不 100% 准确,手动修正需要作为兜底)
**补充建议**：Phase 1 的任务条目应补充为:
- 声纹管线打通（含离线校正 roleType 修复）
- 安全加固 + Spring Security
- 断线补传机制
- 手动修正指令（rename_speaker / regenerate_minutes）
- **P0 缺陷修复**（XfyunRealtimeClient 并发多实例 + AsrBridgeService Bug + ISV HashMap 修复）——应标注为独立任务条，约 2 天工作量,与声纹管线并行

### Phase 2（W3-W4）会后闭环 —— 合理,缺 2 项 + 1 项顺序应提前
图表内容：进度提醒、飞书待办交互、延期标记
评估报告对照: W3 做进度提醒引擎 + 飞书交互, W4 做延期标记 + 升级通知 + 低置信度纠错
**合理性判定**:
- ✅ 进度提醒引擎（4天） -> 合理。 Redis ZSet + 定时扫描,纯工程量
- ✅ 飞书待办交互卡片 -> 合理. 卡片回调 action handler, 2天
- ✅ 延期标记 + 升级通知 -> 合理. 1.5天
- ⚠️ 低置信度 LLM 纠错未标注 | 评估报告 W4 包含（3天工作量）。这是纪要质量提升的关键一步, 缺了则纪要中 ASR 识别错误的专有名词无法自修正
- ⚠️ XfyunRealtimeClient 并发多实例修复应提前到 Phase 1 | 这是 P0 级缺陷（不修只能同时开 1 场会), 虽然代码改动量只有 1 天, 但影响全局并发能力, 不应放在会后阶段
**补充建议**：Phase 2 应增加:
- 低置信度 LLM 纠错（confidence < 0.7 的 transcript 段 → LLM 修正)
- **P0 缺陷修复**应在 Phase 1 完成, Phase 2 才能可靠多实例并发运行

### Phase 3（W5-W8）全闭环 MVP —— 鯏偏乐观,需调整
图表内容：会前状态机、飞书日历/会议室、飞书任务同步、生产部署
评估报告对照: W5 做前状态机 + 参会确认, W6 飞书日历+会议室+定时发起, W7 飞书任务同步+生产部署, W8 压测+全链路验证
**合理性判定**:
- ⚠️ 会前状态机（W5）偏乐观 | 评估报告给出 6 个会前能力点合计 12天工作量（#1-#6），W5 仅 5 天工作日。状态机 + 卡片 + 超时确认 + 关键人判断, 一 周内很难全部做完
- ⚠️ 飞书日历+会议室（W6）偏乐观 | `FeishuCalendarService` 估算 4天, 加上定时发起（2天)和上次纪要附带（1天), 合计 7天, 超出一周。 且飞书日历 API 权限审批需要 1-3 天, 可能卡在审批上
 **飞书任务同步（W7）偏乐观 | `FeishuTaskService` 估算 4天, 加上生产部署配置（3天), 合计 7天. 飞书任务 API 同样需要权限审批
- ✅ 压测+全链路验证（W8）合理 | 篮一周做验证是必要的
**关键风险**: **飞书 API 权限审批是硬性阻塞**。 日历读写、会议室管理、任务管理等组权限需企业管理员审批, 审批周期 1-3 天/组. 如果审批慢, W5-W7 全部可能延后。
**调整建议**: Phase 3 应从 4 周调整为 **5 周**（W5-W9):
 W5-W6 做会前状态机+参会确认, W7 飞书日历+会议室+定时发起, W8 飞书任务同步, W9 生产部署+压测准备; 同时在 W1 提交飞书权限审批申请, 并标注飞书审批为前置依赖.
- 生产部署可以提前到 W6 开始准备（配置/域名/SSL 采购与脚本编写）, 避免 W7 才开始

 导致最后一周才部署

 问题

- W9 独做压测+全链路验证, 留足缓冲空间

 给可能延后 1-2 周的飞书审批留时间.

## 三、遗漏项补充
### 3.1 缺少 P0 缺陷修复标注
图表中没有单独标注 P0 级代码缺陷修复。根据技术可行性评估, 当前有 4 个必须修复的高严重度缺陷:
 | P0 缺陷 | 工作量 | 应放置时间 | 影响 |
|---------|--------|-----------|------|
| `XfyunRealtimeClient` 单例→并发多实例 | 1天 | W1（Phase 1） | 不修只能同时开 1 场会 |
| `AsrBridgeService` 忽略 `rl` + 计数器不递增 | 0.5天 | W1（Phase 1） | 不修所有 segment 都是 Speaker 0 |
| `MinuteGenerationService` 偰纹管线空壳 | 0.5天 | W1（Phase 1） | 不修纪要中无真实姓名 |
| `XfyunIsvClient` HashMap→ConcurrentHashMap | 0.1天 | W1（Phase 1） | 并发注册时数据损坏 |
**建议**: 在 Phase 1 第一周增加一个独立任务条「P0 缺陷修复(2天)」, 与声纹管线并行。

### 3.3 缺少验收标准
图表中每个任务条只写了做什么,没有标注验收标准。参考评估报告中的验收口径,建议补充: | Phase | 关键验收标准 |
