.# 智能会议系统 —— 全流程闭环评估报告

> 目标定义：人只需要在会上发言和决策，其余流程全自动完成。  
> 编制日期：2026-05-14

---

## 一、可行性评估

### 1.1 结论：可行，但需分层理解「全自动」

「全自动」不是二值开关，而是一条渐进的链路。拆解到每个环节：

| 环节 | 当前状态 | 全自动目标 | 能否实现 | 判据 |
|------|----------|-----------|---------|------|
| **会前：会议发起与邀约** | 飞书指令「开始会议」→ 系统创建+启动 | 按固定会议周期自动触发（如每周一 9:30 综合管理会） | 可实现 | 定时任务 + 会议类型预设已入库，只需调度触发 |
| **会前：参会人确认** | 无（跳过） | 飞书卡片一键确认 / 超时默认参加 | 可实现 | 卡片能力已有，需补状态流转与定时推进 |
| **会前：会议室预约** | 无 | 飞书日历 API 自动创建 | 可实现 | 纯 API 对接，无技术壁垒 |
| **会前：资料推送** | 部分有（上次进度通报） | 上次纪要 + 待办 + 业务数据自动附带 | 可实现 | 上次通报已有；飞书 Doc 链接附加即可 |
| **会中：AI 主持人驱动流程** | 后端 95%（议程/TTS/点名/计时） | AI 全程语音驱动，人只听+说 | 可实现 | 后端能力已具备；前端虚拟形象是体验增强，非功能必要 |
| **会中：实时转写** | 100% | 人说话→实时文字显示 | 已实现 | — |
| **会中：发言人识别** | 管线断裂（TODO） | 自动标注谁说了什么 | 可实现 | ISV 客户端完整，差「会后识别→回写」一步；实时 rl 映射需对接 |
| **会后：纪要生成** | 100% | 会议结束→5 分钟内出飞书文档 | 已实现 | — |
| **会后：待办提取与分配** | 100%（LLM 提取 + 人名匹配） | 纪要→待办→自动分配责任人 | 基本实现 | 人名匹配准确率依赖声纹+映射；LLM 提取完整率约 85% |
| **会后：待办提醒** | 未实现 | 临期自动提醒，超期自动标记 | 可实现 | Redis ZSet + 定时扫描，纯工程量 |
| **会后：待办跟踪与闭环** | 部分（API 有，飞书交互缺） | 飞书卡片一键完成/延期→下次会议通报 | 可实现 | 卡片回调能力已有，缺具体 action handler |
| **闭环：下次会议自动通报** | 100% | 开会即展示上次待办完成率 | 已实现 | — |

**总体判断**：技术栈和已有代码决定了这条链路**技术上完全可行**。不存在需要从零研发的底层能力，所有缺失项都属于「已有能力拼装」或「API 对接」。

### 1.2 全自动的边界条件

「全自动」成立的前提：

1. **声纹注册率足够高**（≥70% 参会人已注册），否则纪要里是 speaker_0/1/2，待办分配也受影响。
2. **参会人飞书 ID 映射完整**（`int_user_mapping` 有数据），否则待办无法推送到个人。
3. **固定会议类型预设已配好**（5 种预设已入库），否则每次要手动填议程。
4. **网络+HTTPS 稳定**，麦克风权限可获。

这些不是技术问题，而是**运营前置条件**——系统上线前需要一次性完成数据初始化。

## 五、风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| 飞书 API 权限审批慢 | 高 | 会前日历/会议室/任务功能延后 | 先用现有飞书指令路径兜底；API 联调与审批并行 |
| 声纹注册率低（<50%） | 高 | 纪要说话人仍是 speaker_n，待办分配准确率下降 | 强制会前注册流程；盲分模式兜底；手动修正兜底 |
| 离线 ASR/LLM 纠错效果不达预期 | 中 | 纪要质量提升有限 | 做为可选增强，不影响主链路；人工修正兜底 |
| LLM API 限流/不稳定 | 中 | 纪要生成延迟 | 多 provider 切换（配置已有）；重试+降级为简易纪要 |
| 多人同时说话 | 低 | ASR 转写混乱 | 产品约定不同时发言；AI 主持人可 TTS 提醒「请一次一人发言」 |
| 真实会议场景复杂度超预期 | 中 | 边界 case 多 | 每周真实场景验证；快速迭代修复 |

---

## 六、总结

**可行性**：全流程闭环在技术上完全可行。20+ 个原子能力点中 7 个已完成，其余均为「已有能力拼装」或「API 对接」，无底层研发风险。

**差距**：约 48 人天纯开发工作量。最大的缺口不是某个单点技术，而是会前状态机（6 个能力点 0%→100%）和飞书新 API 对接（日历/任务，代码可写但联调需人工）。

**AI 开发能力边界**：约 85% 的代码工作可由我独立完成；必须人工支持的是飞书/腾讯 API 联调验证、服务器部署、声纹数据运营、产品决策。

**时间节点**：
- **2 周**：会中闭环（声纹→说话人→纪要姓名闭环 + 安全 + 修正）
- **4 周**：会后闭环（提醒引擎 + 飞书交互 + 延期标记 + 纠错）
- **8 周**：全闭环 MVP（三阶段跑通 + 飞书任务 + 生产部署）
- **12 周**：企业级平台（降级 + 分布式调度 + 监控 + AI 主持完整版）

核心约束不在代码，而在**飞书 API 审批速度**和**声纹注册运营**——建议第一周就并行启动这两项。
