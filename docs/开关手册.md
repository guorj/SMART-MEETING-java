# 智能会议系统 - 开关手册

文档版本：2026-06-07  
适用范围：`meeting-server`（`application.yml` + profile 覆盖 + 环境变量覆盖）

---

## 1. 目标与原则

本手册用于统一说明系统中可配置开关（feature flags / runtime toggles）：

- 已实现：可直接通过 yml / 环境变量生效。
- 建议新增：尚未落地，仅做运维与研发规划，不代表当前版本可用。

开关设计原则：

- 同一能力尽量“主开关 + 细分开关”。
- 对外部依赖（飞书、LLM、ASR）优先提供降级开关。
- 对定时任务优先提供 `enabled` 开关，避免误触发。

---

## 2. 配置生效优先级

Spring Boot 常规优先级（高 -> 低）：

1. 环境变量（如 `MEETING_TODO_REMINDER_ENABLED`）
2. profile 配置（如 `application-dev.yml`、`application-prod.yml`）
3. 默认配置 `application.yml`

说明：

- 大部分开关改动后需要重启服务生效。
- 使用 `@ConditionalOnProperty` 的组件（如定时任务）必须重启后才会注册/反注册。

## 3. 已实现开关（当前可用）

## 3.1 会后链路

| 配置键 | 默认值 | 作用 | 影响范围 |
|---|---|---|---|
| `meeting.minute.generation-enabled` | `false` | 会后是否生成纪要主链路 | 关闭后不触发 `MeetingEndedEvent`；与离线转写解耦，不影响 `offline-enabled` |
| `meeting.asr.offline-enabled` | `true` | 会后是否执行讯飞 IST 离线转写 | 会议结束时**独立**触发（Outbox `OFFLINE_ASR`）；有实时定稿分段时跳过；若同时开纪要则**先离线、再纪要** |
| `meeting.minute.llm-enabled` | `true` | 是否调用 LLM 生成纪要初稿 | 关闭后用转写原文 + 简易头作为纪要正文 |
| `meeting.minute.ai-enhancement-enabled` | `true` | 纪要 AI 增强开关 | 关闭后仅保留初稿 |
| `meeting.minute.persist-enabled` | `true` | 是否落库纪要正文 | 关闭后仅保留外链/状态 |
| `meeting.minute.feishu-doc-enabled` | `true` | 是否写入飞书文档 | 关闭后跳过 `createDoc`/`updateDoc`，不写入 `doc_url` |
| `meeting.minute.notify-enabled` | `true` | 纪要完成后是否推送飞书通知 | 关闭后跳过 `pushFeishuCard` |
| `meeting.minute.expose-content-in-api` | `true` | 纪要 API 是否返回全文 | 关闭后 API 仅返回元信息 |
| `meeting.todo.extraction-enabled` | `false` | 是否执行待办提取链路 | 关闭后不发布/不执行待办提取 |
| `meeting.todo.reminder-enabled` | `false` | 待办提醒定时任务总开关 | 关闭后不注册 `TodoReminderScheduler`（含逾期标记/升级/每日汇总三项子任务） |
| `meeting.todo.reminder-cron` | `0 */30 * * * ?` | 逾期自动标记 + 责任人提醒 Cron | 每 30 分钟扫描过 deadline 仍未完成的待办，自动置为 OVERDUE 并提醒责任人 |
| `meeting.todo.escalation-cron` | `0 30 8,17 * * ?` | 延期升级提醒直属上级 Cron | 每日 08:30 与 17:00 两次，按责任人聚合 OVERDUE 待办，向上级发送交互式卡片（含「催办」「已知晓暂不处理」按钮） |
| `meeting.todo.daily-summary-cron` | `0 0 9 * * ?` | 每日未完成待办清单汇总推送 Cron | 每日 09:00 按责任人聚合未完成待办，推送交互式卡片（含每条待办的「申请延期」「挂起」按钮，点击后引导回复理由） |
| `meeting.todo.reason-input-ttl-minutes` | `5` | 申请延期/挂起后理由输入会话 TTL（分钟） | 责任人点击按钮后须在此时长内回复理由文本，超时失效 |
| `meeting.todo.attachment-dir` | `data/todo-attachments` | 待办附件本地目录（冷启动） | 修改后重启 |
| `meeting.todo.attachment-max-bytes` | `10485760` | 单附件最大字节（冷启动） | 默认 10MB |

补充：

- `meeting.todo.reminder-*` / `meeting.todo.escalation-*` / `meeting.todo.daily-summary-*` 三组 Cron 均仅在 `reminder-enabled=true` 时生效（共用 `TodoReminderScheduler` Bean）。
- 延期升级提醒依赖 `int_user_mapping_feishu.supervisor_feishu_user_id`（v0.23 新增列）；未配置上级的用户跳过升级。
- 待办拆分（`POST /api/v1/todos/{tid}/split`）支持将父待办拆分为子待办，子待办 `parent_id` 指向父待办（v0.23 新增列）。
- 每日汇总卡片（`buildDailySummaryCard`）与上级升级卡片（`buildSupervisorEscalationCard`）均为交互式卡片：责任人点「申请延期/挂起」后机器人引导其回复理由（由 `TodoReasonPendingStore` 跟踪会话，5 分钟内有效）；上级点「催办」会向责任人再次提醒并递增 `remind_count`，「已知晓暂不处理」仅记录日志不改变待办状态。

**会后开关组合（2026-06-07 解耦后）**

| offline-enabled | generation-enabled | 会后行为 |
|---|---|---|
| true | false | `PROCESSING` → 离线转写入库 → `COMPLETED`（dev 常用） |
| false | true | 直接纪要（读 DB 实时分段，无则空转写） |
| true | true | `PROCESSING` → 离线转写完成 → 纪要生成 → `COMPLETED` |
| false | false | 直接 `COMPLETED` |

启用 Kafka 时需创建 topic `meeting.offline.asr`（dev 默认 LocalEventBus 无需 Kafka）。

### 会序 oabp 项目任务资料（host_agenda）

在 preset 或会议 `host_agenda` JSON 的会序项增加 `oabpTaskSql`（只读 `SELECT`），主持页 `agenda-doc-content` 会追加「项目任务」表格 part（`sheet_cells`）。

**管理后台**：会务预设 →「会序与资料」页，每项会序底部有 **oabp 项目任务 SQL** 文本框；失焦自动保存。亦可在「host_agenda JSON」高级 tab 手工编辑同字段。

**表**：`oabp.jq_project_task_tracking`（查询时可写表名，默认库为 oabp）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint PK | 主键 |
| `task_name` | varchar(200) | 任务名称 |
| `business_block` | varchar(32) | 所属板块（crm_business_unit 字典） |
| `project_id` | bigint | 所属项目 ID（关联 jq_project.id，可选） |
| `assignee_user_id` | bigint | 责任人（system_users.id） |
| `decision_maker_user_id` | int | 决策人 |
| `progress` | tinyint | 进度 0–100 |
| `last_week_content` | text | 上周跟进 |
| `this_week_plan` | text | 本周计划 |
| `start_date` / `planned_end_date` | date | 开始 / 计划结束 |
| `status` | tinyint | 0 未开始 / 1 进行中 / 2 已完成 / 3 已延期 |
| `remark` | varchar(500) | 备注 |
| `deleted` | bit(1) | 软删，查询建议 `deleted = 0` |
| `tenant_id` | bigint | 租户，多租户环境需在 WHERE 中限定 |

示例（按项目过滤，状态转中文列名）：

```json
{
  "title": "项目任务通报",
  "oabpTaskSql": "SELECT task_name, business_block, progress, CASE status WHEN 0 THEN '未开始' WHEN 1 THEN '进行中' WHEN 2 THEN '已完成' WHEN 3 THEN '已延期' END AS status_label, start_date, planned_end_date, this_week_plan FROM jq_project_task_tracking WHERE deleted = 0 AND project_id = 123 ORDER BY planned_end_date"
}
```

责任人姓名需 JOIN `system_users` 时，可在各会序单独写 SQL，例如：

```sql
SELECT t.task_name, u.nickname AS assignee, t.progress, t.planned_end_date
FROM jq_project_task_tracking t
LEFT JOIN system_users u ON u.id = t.assignee_user_id
WHERE t.deleted = 0 AND t.project_id = 123
ORDER BY t.planned_end_date
```

- 各会序可配置**不同** SQL；未配置 `oabpTaskSql` 则不查 oabp
- SQL 禁止分号与 DML/DDL 关键字；建议 oabp 账号只读 GRANT
- oabp 未启用时，已配置 SQL 的会序返回 part 级 `fetchError`，不阻断飞书/本地资料
- 列名即主持页表头（可用 `AS 中文别名`）；结果集列数/列名因会序而异，由 `sheet_cells` 通用表格渲染

### 会前事项对比通报（weekly-comparison）与 oabp

`feishu-scheduled-bot` 定时 job 的 **SOURCE** 与主持页同源：按 `source_config_names` 定位 preset `host_agenda` docs[]，读取**同一会序项**的 `oabpTaskSql` 查 oabp 库（不再读飞书多维表/docx 作为 SOURCE）。

**v0.26 产出入库**（不再写飞书 Doc）：

- 每次执行 INSERT 1 行 `int_weekly_matter_comparison_run` + N 行 `int_weekly_matter_comparison_item`（一行一事）
- `host_agenda` OUTPUT 行保存 `generatedReportRunId`（指向最新 run）
- `assignee` 缺失存 NULL（前端显示「未提及」）
- `generation_status`：READY（含 0 条）/ PARTIAL（部分丢弃）/ FAILED（整体解析失败）

- 管理后台为各会序配置 SQL 后，须确认 `int_weekly_matter_comparison_job.source_config_names` 与 docs `configName` 一致
- MCP 路径：Agent 经 `meeting-mysql` 执行下发的 SQL（账号需 `GRANT SELECT ON oabp_pro.*`），返回 items JSON 块由 Bot 入库
- Legacy fallback：`MEETING_DB_OABP_ENABLED=true` + Bot `feishu.weekly-comparison.oabp.*`，LLM 产 Markdown 解析为 items
- 详述：[weekly-matter-comparison.md](weekly-matter-comparison.md) · [weekly-matter-comparison-USER-MANUAL.md](weekly-matter-comparison-USER-MANUAL.md)

### 飞书 .base 离线导入 jq_project_task_tracking

将飞书多维表格离线快照（Obsidian 插件导出的 `.base`，内含 `gzipSnapshot`）一次性/幂等写入 `oabp.jq_project_task_tracking`。

**脚本**：[`scripts/import-feishu-base-to-oabp.mjs`](../scripts/import-feishu-base-to-oabp.mjs)（解析模块 [`feishu-base-parser.mjs`](../scripts/feishu-base-parser.mjs)）

**安装与 dry-run（不写库）**：

```powershell
cd smart-meeting-java/scripts
npm install
node import-feishu-base-to-oabp.mjs --file "F:/obsidian/Projects/📋综合管理事项代办清单.base" --dry-run
```

**正式导入**（默认 `DB_OABP_NAME=oabp_pro`；首次需 DBA 执行 [`scripts/sql/bootstrap-oabp-pro.sql`](../scripts/sql/bootstrap-oabp-pro.sql)）：

```powershell
npm run import-feishu-base
# 或 jq_todos + tracking 一并导入
npm run import-feishu-oabp-all
```

可选 `--tenant-id <id>` 覆盖快照内 tenantID。重复执行按 `remark` 前缀 `[feishu:recId=...]` **upsert**，不 truncate 全表。

**字段映射**（飞书 → MySQL）：

| 飞书列 | → 目标列 |
|---|---|
| 待办事项 | `task_name` |
| 项目类别 | `business_block`（中文标签，空则「未分类」） |
| 执行人（第一人） | `assignee_user_id`（`system_users.nickname` 匹配；未命中写 `0`，姓名保留在 `remark`） |
| 执行人（其余） | `remark` 追加「共同执行人：…」 |
| 创建时间 | `start_date` |
| 截止日期 | `planned_end_date` |
| 是否已完成 | `status`：已完成→2；未完成且已过期→3；否则→1 |
| 长期任务 | `remark` 追加「长期任务：…」 |
| — | `progress`：已完成→100，否则→0 |
| — | `project_id`：NULL |
| — | `tenant_id`：快照 tenantID（可用 CLI 覆盖） |
| — | `remark` 前缀 `[feishu:recId=…]` 用于幂等 |

**导入后会序 SQL 示例**（综合管理会全表待办）：

```sql
SELECT task_name, business_block, progress,
  CASE status WHEN 0 THEN '未开始' WHEN 1 THEN '进行中' WHEN 2 THEN '已完成' WHEN 3 THEN '已延期' END AS status_label,
  planned_end_date, remark
FROM jq_project_task_tracking
WHERE deleted = 0 AND remark LIKE '[feishu:recId=%'
ORDER BY planned_end_date
```

**验收**：

```sql
SELECT status, COUNT(*) FROM jq_project_task_tracking
WHERE remark LIKE '[feishu:recId=%' GROUP BY status;
```

**单元测试**（纯解析，不连库）：

```powershell
npm run test:import-feishu-base
```

幂等规则：

- 主任务：`jq_todos_task.remark = [feishu:recId={recId}]`
- 子任务：每位执行人一条，`remark = [feishu:recId={recId}:sub={i}]`；重导时多余旧 subtask **软删**（`deleted=1`）
- 不 truncate；库内非飞书前缀的手工数据保留

**字段映射**（飞书 → MySQL）：

| 飞书列 | jq_todos_task | jq_todos_subtask |
|---|---|---|
| 待办事项 | `task_name` | `task_name`（同名） |
| 项目类别 | `business_block` | — |
| 创建时间 / 截止日期 | `start_date` / `planned_end_date` | — |
| 是否已完成 | `status`、`progress` | — |
| 长期任务 | `task_detail` | — |
| 执行人[i] | — | `asignee_id`（`system_users.nickname`；未命中 `0`） |
| — | `decision_maker_user_id`：`0`（待后续在 oabp 指定决策人） | — |
| — | `remark` 幂等键 | `remark` 幂等键 |
| — | `tenant_id`：快照 tenantID（bigint 字符串） | `tenant_id`：`0`（subtask 列为 int，超大 tenant 溢出） |

**会序 oabpTaskSql 示例**（主任务 + 子任务执行人 + 跟进表；一行一条主任务，执行人合并，表头中文；组序 **已延期 → 已完成 → 进行中 → 未开始**；组内 **已完成按截止日期倒序、进行中按剩余时间升序**）：

完整 SQL 见 [`scripts/sql/oabp-task-agenda-jq-todos.sql`](../scripts/sql/oabp-task-agenda-jq-todos.sql)，粘贴到 preset / 会议 `host_agenda` 的 `oabpTaskSql` 即可。

主持页是否展示：同会序项 JSON 字段 `oabpTaskShow`（默认 `true`）；管理后台 oabp SQL 区有 **「主持页展示」** 复选框。

每条资料绑定（飞书链接 / 本地上传）另有 `showInHost`（默认 `true`）；管理后台资料卡片上也有 **「主持页展示」** 复选框。设为 `false` 时资料仍保留（weekly-comparison 等仍可用），主持页不渲染该资料。

```sql
SELECT
  t.task_name AS `待办事项`,
  t.business_block AS `项目类别`,
  GROUP_CONCAT(DISTINCT u.nickname ORDER BY s.id SEPARATOR '、') AS `执行人`,
  t.progress AS `进度`,
  CASE t.status
    WHEN 0 THEN '未开始'
    WHEN 1 THEN '进行中'
    WHEN 2 THEN '已完成'
    WHEN 3 THEN '已延期'
  END AS `状态`,
  t.start_date AS `开始日期`,
  t.planned_end_date AS `截止日期`,
  NULLIF(TRIM(t.task_detail), '') AS `长期任务`
FROM oabp_pro.jq_todos_task t
-- ... JOIN / WHERE / GROUP BY 同 sql 文件（表名均 oabp_pro. 前缀）...
ORDER BY
  CASE t.status WHEN 3 THEN 0 WHEN 2 THEN 1 WHEN 1 THEN 2 WHEN 0 THEN 3 ELSE 4 END,
  /* 已完成 DESC / 进行中 ASC — 见 sql 文件 */
  t.id
```

### oabp 库读写能力（双常用库架构）

`meeting.datasource.external.oabp.enabled=true` 时，oabp 升级为系统常用库，支持后台业务读写。

**架构分层**：

| 层 | 组件 | 数据源 | 用途 |
|---|---|---|---|
| 前台只读 | `OabpAgendaTaskQueryService` + `OabpReadOnlySqlValidator` | oabp（JdbcTemplate） | 会序 `oabpTaskSql` 动态查询，受 `max-query-rows`/`query-timeout` 约束 |
| 后台读写 | `OabpJqTodosTaskMapper` / `OabpJqTodosSubtaskMapper` / `OabpJqTodosTaskFollowupMapper` | oabp（MyBatis-Plus + XML） | 业务代码直接 CRUD，不受前台限制 |
| 跨库一致性 | `OabpTaskWritebackConsumer` / `OabpFollowupSyncConsumer` + `OabpOutboxPublisher` | oabp（`oabpTransactionManager`） | meeting 主库事务提交后异步写 oabp，走 `int_event_outbox` 重试 |

**事务约定**：
- 写 oabp 必须显式 `@Transactional("oabpTransactionManager")`
- 跨库写入（同时写 intelligence + oabp）禁止用同一 `@Transactional`，必须走 Outbox 异步
- 主库事务内调用 `OabpOutboxPublisher.publishTaskWriteback(...)` 发布领域事件，`AFTER_COMMIT` 阶段写 outbox

**Mapper 包约定**：
- oabp Mapper 必须放在 `com.smartmeeting.repository.oabp` 子包
- oabp XML 必须放在 `classpath*:/mapper/oabp/**/*.xml`
- 主库 Mapper/XML 路径不变，两库物理隔离

**Outbox 事件类型**（`OutboxEventTypes`）：
- `OABP_TASK_WRITEBACK`：待办回写 `jq_todos_task`（状态/进度）
- `OABP_FOLLOWUP_SYNC`：跟进同步 `jq_todos_task_followup`（跟进文本）
- `OABP_SUBTASK_SYNC`：执行人同步 `jq_todos_subtask`（asignee_id，v0.27 新增）
- 消费者失败由 `OutboxPoller` 重试 8 次，超限转 `FAILED`

**OABP 三表分工**（v0.27 起）：

| OABP 表 | 字段 | 同步触发点 | 事件类型 |
|---|---|---|---|
| `jq_todos_task` | `status` (0/1/2/3) + `progress` (0-100) | 待办首次创建 / 添加进度 / 状态变更 / 决策裁决 | `OABP_TASK_WRITEBACK` |
| `jq_todos_task_followup` | `followup_content` / `last_week_progress` / `this_week_plan` | 添加进度（写跟进文本） | `OABP_FOLLOWUP_SYNC` |
| `jq_todos_subtask` | `asignee_id` (int，OABP system_users.id) | 待办首次创建（建执行人记录） | `OABP_SUBTASK_SYNC` |

**meeting TodoStatus → OABP status 映射**（`OabpTodoStatusMapper`）：

| meeting TodoStatus | OABP status | 说明 |
|---|---|---|
| `PENDING` | 0 | 未开始 |
| `IN_PROGRESS` / `BLOCKED` / `OVERDUE` / `PENDING_DECISION` | 1 | 进行中（兜底） |
| `COMPLETED` | 2 | 已完成（progress 同步置 100） |
| `DELAYED` | 3 | 已延期 |

**责任人 ID 反查**：`OabpAssigneeResolver.resolveOaUserId(feishuUserId)` 按 `int_user_mapping_feishu.feishu_user_id` 反查 `user_id`（即 OABP `system_users.id`），写入 `jq_todos_subtask.asignee_id`。查不到映射时跳过 subtask 同步（只同步 task + followup）。

**决策人来源**：`OabpDecisionMakerResolver.resolve(meetingTodoId)` 按 remark 前缀 `[meeting:todoId=xxx]` 查 `jq_todos_task.decision_maker_user_id`，经 `FeishuUserIdResolver` 解析为飞书 user_id。值为 0 或解析失败时待办直接走原完成流程（不推决策人裁决）。

**与流水线的关系**：本包消费者可被未来 Pipeline StepExecutor 复用——流水线步骤的 `step_type` 可指向消费者类名，由 Pipeline 执行器反射调用。当前阶段先由 OutboxPoller 驱动。

## 3.5 待办二段式裁决 + OABP 三表同步（v0.27）

### 流程概览

```
会议结束 → TodoExtractionService 提取待办
            ├─ 同步 OABP: jq_todos_task INSERT (status=0,progress=0)
            └─ 同步 OABP: jq_todos_subtask INSERT (asignee_id=反查OABP工号)

POST Pipeline: post-feishu-task-sync
  └─ 向责任人推送待办卡片（提交完成/挂起/更新进度）

责任人操作:
  ├─ 添加进度 → TodoProgressService.addProgress
  │    ├─ 同步 OABP: jq_todos_task UPDATE (progress, status)
  │    └─ 同步 OABP: jq_todos_task_followup INSERT (跟进文本)
  ├─ 点"提交完成" → TodoService.applyAssigneeComplete
  │    ├─ 查 OABP decision_maker_user_id
  │    ├─ 有决策人 → 置 PENDING_DECISION + 推裁决卡 + 同步 task.status=1
  │    └─ 无决策人 → 置 COMPLETED + 同步 task.status=2 + progress=100
  └─ 进度/附件 → Web dashboard（MeetingTodoProgress/Attachment 表）

决策人操作:
  └─ 点裁决完成/延期/驳回 → TodoService.applyDecisionMakerDecision
       ├─ 置终态（COMPLETED/DELAYED/IN_PROGRESS）
       └─ 同步 OABP: jq_todos_task UPDATE (status)
```

### 状态流转

```
PENDING / IN_PROGRESS
   ↓ (责任人提交完成 + 有决策人)
PENDING_DECISION
   ↓ (决策人裁决)
COMPLETED / DELAYED / IN_PROGRESS（驳回）
```

- 责任人无决策人时：`PENDING/IN_PROGRESS → COMPLETED`（原流程）
- `PENDING_DECISION` 态责任人不可直接改状态，须由决策人裁决
- `OVERDUE` 仍由系统定时任务维护，不可手动设置

### 数据模型（v0.27 schema-upgrade）

`int_meeting_todo` 新增 6 列：

| 列 | 类型 | 说明 |
|---|---|---|
| `decision_maker_feishu_user_id` | VARCHAR(64) NULL | 决策人飞书 user_id（缓存，避免每次回调重查 OABP） |
| `decision_maker_name` | VARCHAR(100) NULL | 决策人姓名（展示用） |
| `pending_decision` | TINYINT(1) DEFAULT 0 | 是否处于已提交待裁决态 |
| `decision_made_at` | DATETIME NULL | 决策时间 |
| `decision_result` | VARCHAR(16) NULL | APPROVED / DELAYED / REJECTED |
| `decision_note` | TEXT NULL | 决策备注 |

索引：`idx_todo_pending_decision (pending_decision, decision_made_at)` 供超时扫描。

### 卡片与回调

| 卡片 | 接收人 | 按钮 | cmd |
|---|---|---|---|
| 待办操作卡（`buildTodoActionCard`） | 责任人 | 提交完成 / 挂起 / 更新进度（跳转 Web） | `todo-action` |
| 决策人裁决卡（`buildDecisionMakerCard`） | 决策人 | 裁决完成 / 裁决延期 / 驳回 | `todo-decision` |

回调路由（`FeishuCommandHandler`）：
- `todo-action` + `complete_todo` → `TodoService.applyAssigneeComplete`（二段式裁决入口）
- `todo-action` + `block_todo` → `TodoService.updateStatusByAssigneeCallback`（置 BLOCKED）
- `todo-decision` + `APPROVED/DELAYED/REJECTED` → `TodoService.applyDecisionMakerDecision`

### Pipeline 配置

| step_type | 作用 | config_json |
|---|---|---|
| `post-feishu-task-sync` | 会议结束后批量发待办卡给责任人 + 同步飞书任务中心 | 无 |
| `post-todo-action` | 裁决超时扫描：向超时未裁决的待办重发裁决催办卡 | `{"timeoutDays": 3}`（默认 3 天） |

### REST API

| 方法 | 路径 | 用途 |
|---|---|---|
| `POST` | `/api/v1/todos/{tid}/submit-complete` | 责任人提交完成（二段式裁决入口） |
| `PUT` | `/api/v1/todos/{tid}/status` | 更新状态（原接口，PENDING_DECISION 态不可用） |
| `GET/POST` | `/api/v1/todos/{tid}/progress` | 进度列表 / 添加进度 |
| `GET/POST` | `/api/v1/todos/{tid}/attachments` | 附件列表 / 上传 |

### 权限校验

- `requireAssignee`：责任人可提交完成、挂起
- `requireDecisionMaker`：决策人可裁决（校验 `todo.decisionMakerFeishuUserId`）
- `requireAssigneeOrOperator`：责任人或经办人可更新进度、上传附件

会前建议完成组织级声纹注册（工作台入口）；会后纪要正文将带「姓名: 发言」格式（识别失败时保留 `speaker_N`）。

**双场景说明（确定参会人 / 临时会 / 会中临时加人）**：

- IST：有 ≥2 条 featureId（participant 行或联查声纹库）时 `auto` 走声纹辅助分离；否则盲分。
- ISV：**全库** 1:N，不按参会人表过滤；临时列席、嘉宾只要在 `int_voiceprint` 已注册即可标名。
- `search-top-k-max` 建议大库拉满 `10`；误标风险靠 `match-score-threshold`、簇级投票与按租户拆 ISV `groupId` 控制。
