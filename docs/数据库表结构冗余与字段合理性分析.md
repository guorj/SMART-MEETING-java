## 4. 冗余与数据重叠分析

### 4.1 `int_meeting` 与 `int_meeting_type_preset` 的维度字段（company / department / group_name）

- **现象**：两表均存公司、部门、会议组等。
- **性质**：属于**有意反规范化**。会议创建后可能脱离预设独立展示；类型 6「其他」或无预设时，会议行需自带维度信息。
- **风险**：预设变更**不会**自动回填已创建会议；历史会议保留创建时快照，与预设**可能长期不一致**（属产品策略，非表设计错误）。
- **结论**：**非冗余表**，存在**可控的数据重复**；若希望强一致，需产品规则（创建时复制 / 定期同步 / 仅存 `preset_type_code` 展示时 JOIN）而非简单删列。

### 4.2 `host_agenda`：预设表 vs 会议表

- **现象**：`int_meeting_type_preset.host_agenda` 与 `int_meeting.host_agenda` 均为 JSON。
- **代码策略**：主持议题解析顺序为「开始请求 `items` → 预设 `host_agenda` → 会议 `host_agenda` → 默认 JSON → 硬编码」（见 `MeetingHostSessionService#resolveTopics`）。
- **结论**：**模板与实例分离**，合理；会议行可覆盖预设，**不是无效重复**。建议业务上明确：**何时写入会议 `host_agenda`**（首次保存快照 / 用户编辑后），并在文档中写明，避免双处长期不同步却无规范。

### 4.3 `participants_names`（预设 TEXT）与 `int_meeting_participant`

- **现象**：两处都可表达「与会人」。
- **代码事实**：**检点**只解析 `int_meeting_type_preset.participants_names`；`int_meeting_participant` 用于参会确认、声纹、待办统计等（见 `TodoExtractionService`、`MinuteGenerationService` 等路径）。
- **风险**：预设名单与参会人表**两套真相**，可能出现「检点点名 A，但 participant 表无 A」或相反。
- **结论**：**语义重叠、来源不统一**，属于**产品/模型层冗余风险**，不是删一张表能解决的；若长期要一致，需规划「以 participant 为权威并生成检点名单」或「创建会议时从预设同步 participant」等策略。

### 4.4 声纹 `feature_id`：`int_meeting_participant` 与 `int_voiceprint`

- **现象**：两处均可存讯飞特征 ID。
- **性质**：全局声纹库（`int_voiceprint`）与**某会议某参会人**绑定（`int_meeting_participant.feature_id`）属于不同粒度，通常**不算重复表**，但存在**字段语义重叠**。
- **建议**：在内部设计文档中约定「以哪张表为注册源、会议行是否仅引用」；避免两处长期双写且不一致。

### 4.5 `doc_url` + `doc_token`、`recording_url` + `recording_token`

- **性质**：URL 与 token 可互相推导一部分场景，属于**存取便利与容错**的常见组合，**可接受**。
- **建议**：注释或文档中标明优先级（例如纪要优先 `doc_token` 调 API），避免业务层同时维护两套且冲突。

### 4.6 `agenda`（会务 JSON 字符串数组）与 `host_agenda`（主持 items JSON）

- **结论**：**语义分离**，非冗余；DDL 注释已说明。保持两列命名清晰即可。

## 5. 字段合理性与缺口

### 5.1 `host_agenda` JSON 形态与注释

- **DDL 注释**仍写为 `{"items":[{"title","minutes"}]}`。
- **应用层**已支持 `items[].detail`（Markdown 等），实体注释可同步扩展，**无需改列类型**（JSON 可演进）。
- **建议**：更新 `schema.sql` / 迁移脚本中的 COMMENT，与 `HostAgendaItemDto` 及前端约定一致，减少运维误解。

### 5.2 `int_meeting.status` VARCHAR(30)

- **合理性**：状态机多变时用字符串可接受；若状态枚举稳定，可考虑 CHECK 或应用层枚举集中管理，**非必须改表**。

### 5.3 `int_transcript_segment`：`speaker_id` 与 `speaker_name`

- **合理性**：标识与展示名分离，利于 ASR 输出 `speaker_0` 与后续人名解析并存；**合理**。

### 5.4 `int_voiceprint.user_id`（INT，OA）与其它表飞书 VARCHAR

- **现象**：跨表用户主键类型不统一（OA 整型 vs 飞书字符串）。
- **性质**：历史集成常见；**非表内冗余**，但增加 JOIN/映射心智负担。
- **建议**：在 `int_user_mapping_feishu` 为枢纽的前提下，新功能尽量**显式经过映射层**，避免隐式混用。

### 5.5 `int_meeting_todo`：`assignee_name` 冗余

- **性质**：相对 `assignee_id` 的**反规范化**，便于列表展示与导出；**可接受**。若责任人改名，历史待办是否更新属产品策略。

### 5.6 `int_matter_progress_doc_config`

- **字段**：`feishu_doc_url` 与 `feishu_doc_token` 二选一或组合，与 4.5 同类，**合理**；`config_name` UNIQUE 支持多路配置，**合理**。
- **生产实测**：见 **§2.2**，生产与仓库 DDL 存在分叉（含 `test_document_text`、长度与索引差异）；以仓库为准的「合理性」评估需待 **结构对齐** 后再定稿。

### 5.7 索引（简要）

- `int_meeting`：status、creator、previous、company+group — **与列表/闭环查询匹配**，未见明显多余索引。
- `int_transcript_segment(meeting_id, start_time_ms)` — **利于按会议拉时间序**，合理。
- `int_meeting_todo(status, deadline)` — **利于待办看板**，合理。

## 6. 综合结论

| 维度 | 结论 |
|------|------|
| **是否存在「多余整张表」** | **否**；8 张表各担一责。 |
| **是否存在需警惕的冗余** | **是**：预设 `participants_names` 与 `int_meeting_participant` **双轨「与会人」**；会议与预设**维度字段**、**host_agenda** 的**业务层同步策略**需文档化。 |
| **字段整体是否合理** | **整体合理**；JSON 主持议程与飞书多维字段与当前主持/纪要/待办能力匹配。 |
| **建议优先动作（不改表也可做）** | ① 更新 `host_agenda` 的 DDL COMMENT 含 `detail`；② 文档写明检点名单来源与 participant 表关系；③ 若二期要统一名单，再定「同步任务或单一权威源」的迁移方案。 |
| **生产对齐（本次实测）** | 收敛 `int_matter_progress_doc_config` 与仓库 DDL；修复表/列 **COMMENT 乱码**；评估 `int_meeting.chat_id` 长度是否需与仓库一致（100）。 |
